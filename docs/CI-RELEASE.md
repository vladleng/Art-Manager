# CI и выпуск Windows-кандидатов

Контракт #83; единственный действующий pipeline — [Windows App Build](../.github/workflows/windows-build.yml).

## Автоматические проверки

Каждый PR получает обязательный итоговый check **CI Gate** (не использовать `paths-ignore`: пропущенный workflow оставляет required check в pending). Планировщик читает diff относительно базы PR; переименования/удаления учитываются Git. Проверяются синтаксис workflows (actionlint с закреплённой версией и SHA256), политика CI и diff.

- Только Markdown в корне/`docs/`: Windows runner не выделяется. Проверка логики и смысла документации остаётся обязанностью автора/reviewer.
- Узкий allowlist UI-компонентов, реально входящих в native UI-набор: `TaskTree`, `TaskTreeRows`, `TaskQuickProperties`, `BlockEditor`, `DayCalendarPanel`. Запускаются `WorkspaceNavigationTests`, `BlockEditorTests`, `GeneralTaskTests`, `TaskTreeUiTests`, затем компиляция Desktop. Это адресный профиль, не доказательство полной регрессии.
- Модель, хранение, тесты, assets, workflows, CMake, неизвестные пути, смешанные изменения: все зарегистрированные CTest, затем Desktop. Не определять косметику по имени ветки.
- Push в `main` и ручной `check`: полный профиль. Ручной запуск не имеет надёжной базы PR, поэтому последний docs-коммит не может скрыть предыдущие изменения ветки.

Версия и список всех тестов берутся из CMake. После configure список сравнивается с реальным CTest JSON; неизвестная регистрация, пустой набор, отсутствующий target или mismatch — ошибка, а не успешный skip. При добавлении тестов менять соответствующие регистрации CMake; CI не содержит второго списка полного набора.

Тесты выполняются один раз, с таймаутом и `--no-tests=error`. UI-набор уже создаёт PNG в `build/`; повторный прогон ради preview отсутствует. Тестовые журналы/JUnit/configure logs и PNG сохраняются даже при падении, срок — 7 дней. Не маскировать FAIL повторными попытками/`continue-on-error`. CTest намеренно последователен: пока независимость всех тестов не доказана, массовое распараллеливание создаёт риск конфликтов. Сборка использует `--parallel 2`.

Кэш содержит только JUCE source tree, ключ включает ОС и CMake. Нет кэша бинарников/результатов/CTest; при изменении JUCE key меняется. Устаревшие PR-прогоны отменяются; ручной выпуск не отменяется новым push. На PR нет write-token, нет `pull_request_target`; checkout не сохраняет credentials.

## Кандидат и Release

Автоматические PR/main проверки **не загружают runtime-пакет**. Для кандидата:

1. Actions → Windows App Build → Run workflow → нужная опубликованная ветка.
2. `mode=candidate`, `version` — точная строка CMake, включая суффикс. Ошибка/пустой ввод останавливает запуск до Windows.
3. Полный CTest → Desktop → проверка JUnit: каждый зарегистрированный тест ровно один раз, без failure/error/skipped/notrun/disabled → ZIP и SHA256.
4. Пакет/manifest/имя Windows job/диагностики получают ту же версию; manifest содержит SHA, run ID, список тестов и хэш EXE. ZIP хранится 14 дней.

Для Release: тот же запуск, **только `main`**, `mode=release`, точная версия. Release job зависит от успешных Windows и CI Gate, скачивает пакет **из этого же run**, проверяет checksum и создаёт **draft** с target равным протестированному SHA. Существующий tag/release не перезаписывается. Не использовать `workflow_run` с произвольным скачиванием артефактов стороннего PR.

Заголовок проверочного run — `Art Manager CI`; GitHub вычисляет `run-name` до чтения checkout. Для `candidate/release` имя run получает проверяемый version input, без второго захардкоженного номера версии. Версии приложения и история ранее принятых выпусков этой настройкой не меняются.

Публикация draft, ручная native/DPI приёмка и merge — отдельные явные решения пользователя. CI PASS их не заменяет. Ручной Release не запускать для проверки настройки: package gate проверяется unit-fixtures и отдельно полным Windows-кандидатом.

## Защита репозитория и ограничения

Для запрета merge до проверок требуется защита `main` с required check **CI Gate**, strict up-to-date и запретом force-push/delete; рекомендуемый источник check — GitHub Actions. Конфигурация YAML сама по себе не защищает прямой push и не запрещает владельцу публиковать Release вручную через GitHub API/UI. Фактическую настройку защиты проверять отдельно; не утверждать, что защита включена на основании наличия workflow.

Исторический `manager-ui.yml` больше не запускается по push и не собирает пакеты; ручной запуск сообщает о переходе на общий workflow и завершается ошибкой. Старые версии YAML в уже существующих ветках/коммитах не переписываются этой правкой; для дальнейшей работы обновить ветку актуальными CI-изменениями после принятия.
