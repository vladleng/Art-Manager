# Рабочее пространство — действующая модель и границы

**Обновлено 2026-11-01:** самостоятельная Windows-версия **0.2.5 принята**. Источники MR Live → позже MR Studio остаются будущими интеграциями, не prerequisite локального Manager 0.2/0.3/0.4/0.5. Перед интеграцией повторно проверять native схемы и ревизии — исторические ссылки не гарантируют актуальность.

## Фактическая база (0.2.5 в main)

- C++20 / JUCE 9, локальный версионированный Workspace JSON **schema 2**, offline legacy song catalog и backup. Studio Pro runtime/Hub/ARA выведены из Windows-продукта (#7/0.2.0); сохранённые задачи/Notes/IDs доступны без DAW.
- Слои: `WorkspaceModel/Store`, `WorkspaceCommands/Queries/Controller`, `WorkspaceShell`, `TaskTree`, `BlockEditor`; GUI вызывает доменные команды, проверенное сохранение/restore с ревизиями и backup.
- Тип `page` — список задач (без прежних вкладок «Содержимое/Задачи»); тип `note` — самостоятельный блочный документ. Старые блоки на `page` **не удалены**, доступны через меню «Открыть прежние материалы». Явное перемещение блоков с backup ещё впереди (#61/#68).
- Обычные `WorkspaceTask` имеют устойчивые ID, один `ownerPageId`, необязательный `parentTaskId`, свойства (название, статус, P1–P4, Notes), блоки и checkpoint records; архивирование/перемещение сохраняют IDs. Модель TaskDomain #54 поддерживает вложенную иерархию, а checkpoint legacy записи не конвертируются молча.
- Поиск, фильтры статуса/приоритета, сортировка и индивидуальные настройки представления (`0.2.5 / #65`) — **UI-проекции** через `WorkspaceTaskViews`, сохраняются в ApplicationProperties, не в Workspace JSON. Сортировка не меняет исходный порядок; данные не дублируются. Принято, Windows #109 10/10 PASS.
- «Сегодня», общий календарь и Timeline работают в будущем поверх **того же task ID**, а не самостоятельных редактируемых копий. Поля дат и отдельные события ещё не добавлены (#38–#40).
- **Нет** MR Live/Studio adapter, нативного write-back и двойной синхронизации; только обсуждённый контракт #48/#49.

## Контракт MR Live, затем MR Studio

1. #48 проверяет native `.mrlive`, существующие IDs/commands, границы рабочего item/Browser version и повторных setlist occurrences. Путь/имя/номер строки не идентичность.
2. Browser layout schema1/v5, demo show v3 и native show v2 в изученном контракте не взаимозаменяемы. Layout не содержит show/tasks. Совместимость версий подтверждается fixtures, неизвестные/будущие версии не перезаписываются.
3. Первый adapter читает согласованный источник или metadata snapshot и явно показывает revision/time, stale/missing и read-only. Публичный API/IPC не считается существующим только по наличию JSON.
4. Write-back — отдельный срез через команды источника: полевая ответственность, revision guard, Undo, повторяемость, save/recovery. Не менять открытый `.mrlive`/`.mrsproject` сторонней заменой всего файла. Save show и Save for All различаются.
5. Source adapters не создают audio backend/transport/host. Вся загрузка/сериализация/IPC вне audio callback. Manager не должен мешать Live performance.
6. #49 повторно использует принятый контракт для Studio после Live; Studio → Live Playback export MR-Studio#291 — другое направление.

### Статусы, приоритеты и progress

Сохранить все Manager статусы (включая POOL/DRAFT/BLOCKED), P1–P4, Notes/порядок/архив. Browser Live использует Todo/Wip/Wait/Done; нужна явная политика неподдержанных значений. Default P3 Manager и P4 Live не меняют сохранённые записи.

Legacy Manager PROG считает DONE среди размеченных треков и задач верхнего уровня; checkpoint progress — DONE/active checkpoints. Browser Live organizer рекурсивно усредняет дочерние проценты. Native правила перепроверяются в #48; нельзя объявить эти показатели одинаковыми или завершать родителя по проценту автоматически. Источник и смысл progress видны пользователю. Календарные даты не меняют музыкальную геометрию show.

## UI и доставка ресурсов

#47 внедряет scoped Manager-профиль существующего MR UDS: manifest semantic IDs, tokens/manager.json, templates/icons. Reference SVG с фиктивными именами/показаниями не является runtime-данными. Нужны закреплённая ревизия, provenance и offline-пакетирование; не сетевой download ассетов в UI и не второй Theme. Конкретная геометрия/контролы Manager остаются назначенным срезом, а не копией всей DAW.

Обычные задачи, поиск, календарь и GPT ориентированы на самостоятельный Manager. Новый VST3/ARA мост со Studio Pro не разрабатывается. Существующий Hub/Inspector — legacy до выполнения #7.

## Совместимость, экспорт и удаление legacy

#7 выводит Studio Pro зависимость с сохранением workspace, старых catalog records, task/checkpoint IDs, Notes keys, порядка, статусов/типов/приоритетов, архивов и backups. Отсутствие старого `.song` не удаляет локальные задачи. Не конвертировать `.song` в `.mrlive` и не удалять пользовательские исходники по предположению. #19 `.show` отменена как not planned; закрытые writer/ARA исследования не возобновляются.

Экспорт workspace включает версию, записи/блоки/ID, локальные данные и проверенные source references. Он не копирует WAV/plugins/проекты автоматически и не содержит API-токенов. Импорт проверяет ссылки, конфликты IDs, source kind и версии; relink меняет локатор, сохраняя идентичность. Архив/удаление связи не удаляет внешний документ. До schema migration — точная backup, идемпотентность и явное восстановление; ошибка не подменяет текущий документ пустым.

## Остальные этапы

План дня/календарь/Timeline используют общую модель дат и IDs. Первые источники аналитики проверяются отдельно (YouTube/VK — кандидаты), с реальными единицами/лимитами/доступом.
