# AGENTS.md — правила разработки Arranger Manager

Область действия: весь репозиторий **vladleng/Art-Manager** (прежний адрес Arranger-Manager перенаправляет сюда). Эти правила обязательны для новых сеансов ChatGPT/Codex и для разработки в тематических ветках. Отвечай пользователю по-русски, коротко и по фактам.

## 1. Продукт и действующие решения

- Arranger Manager — **самостоятельное рабочее пространство** экосистемы MR: страницы, задачи, план дня, календарь, Timeline, аналитика и GPT-помощник. Обычные задачи должны работать локально без DAW, сети или запущенных MR-приложений.
- Решение от **2026-10-28**: прежняя функциональная связь с Fender Studio Pro **упразднена**. Первый музыкальный источник — **MR Live**, следующий, отдельный этап — **MR Studio**. Не начинать новые `.song`/`.show` readers/writers, ARA/context bridge или Studio Pro extensions.
- Существующие Studio Pro reader/Hub/Inspector — **legacy**, пока #7 не выведет зависимость безопасно. Не удалять пользовательские `.song`, `.show`, медиа и локальные задачи; не представлять перепланирование как готовую интеграцию.
- Канонические документы: [HANDOFF](docs/HANDOFF.md), [MR-ECOSYSTEM](docs/MR-ECOSYSTEM.md), [WORKSPACE-ARCHITECTURE](docs/WORKSPACE-ARCHITECTURE.md), [ROADMAP](docs/ROADMAP.md), [CONCEPT](docs/CONCEPT.md). Основной план — #36, ядро — #37. Исторические `HYBRID-*`, `HUB-*`, `CONTEXT-BRIDGE-*` и ARA-материалы не переопределяют решение 2026-10-28.
- Текущий код/статус определяй по **актуальным main, рабочей ветке, PR, Issue и CI**, а не по устаревшей строке в документации. При конфликте: явное последнее решение пользователя → назначенный Issue/его критерии → действующие документы → исторические записи. Не приписывать приёмку по одному успешному CI.

## 2. Начало каждого нового сеанса

1. Прочитать этот файл, затем проверить репозиторий, default branch, рабочую ветку, HEAD и состояние незакоммиченных изменений (если есть checkout). Ничего не сбрасывать, не перезаписывать чужие изменения.
2. Изучить **назначенный Issue**, родительскую задачу, связанные открытые PR и актуальные критерии приёмки. Если Issue не назначен, сначала найти подходящий существующий или оформить новый перед изменениями.
3. Читать нужные разделы HANDOFF, MR-ECOSYSTEM и профильной документации. Не загружать весь `docs/` и все исходники без необходимости; искать по компоненту/сущности/ошибке.
4. Сверить последние коммиты и Actions нужной ветки; проверить, что описание предыдущего чата не устарело.
5. Выполнить **только порученный срез**. Не начинать следующий Issue или интеграцию автоматически. При изменении требований сначала согласовать/обновить scope и чек-лист.

Рабочий цикл: **Issue → короткий план/контракт → целевой код → адресные проверки → Windows-кандидат при необходимости → пользовательская приёмка → merge → отчёт в Issue**.

## 3. Git, Issues, PR и приёмка

- **Issue-first.** Одно самостоятельное изменение — один понятный Issue или согласованный sub-issue с результатом, границами и критериями проверки. Дополнения внутри того же объёма не смешивать со следующими этапами.
- Новая ветка — от **принятого main**; для явно согласованной цепочки PR допустима другая base branch (например, UI над непринятой 0.1h). Перед началом проверять base/head; не терять изменения параллельной работы.
- Изменения и нужные документы публиковать в **тематической ветке и PR**. Не коммитить напрямую в main, не делать force-push/reset чужой истории и **не сливать PR без явной пользовательской приёмки этого объёма**.
- PASS сборки, тестов, snapshot или артефакта означает техническую проверку, а **не** пользовательскую приёмку. PR может оставаться draft до неё. Закрывать Issue только после принятия соответствующего результата; родительский Issue не закрывать автоматически.
- Не исправлять посторонний код, не запускать масштабный рефакторинг и не обновлять зависимости «заодно». Критичное обнаруженное отклонение записать в отдельный Issue.
- В PR указать: связанный Issue, изменения, не вошедший объём, реальные проверки, риски/миграции, ссылку на пакет и явный статус приёмки.

## 4. Версии и артефакты

- **Версионирование Manager не путать с MR Studio/MR Live.** Действующая линия Manager: шаги **0.1e–0.1j** внутри выпуска 0.2; дальнейшие целевые выпуски 0.3 (день), 0.4 (календарь), 0.5 (Timeline), 0.6 (аналитика), 0.7 (GPT). Номер GitHub Issue, PR или Actions run **не является номером версии**.
- Исправления уже назначенной версии маркировать `-fix1`, `-fix2`, …; небольшие функциональные дополнения в том же срезе — `-Upd1`, `-Upd2`, …, **если такой суффикс закреплён в Issue/PR**. Существенный новый объём выносить в отдельный Issue; принятые версии не переименовывать задним числом. Не переносить автоматически схему `0.I.S` MR Studio на Manager без отдельного решения.
- Для публикуемого кандидата **версия приложения/пакета и имена всех артефактов одной сборки должны совпадать** с объявленной версией, включая `fix/Upd`. Если имя workflow/run ещё не содержит этой версии, указывать ограничение и согласовать синхронизацию CI, а не утверждать, что правило уже реализовано.
- Не менять CMake project version, имена пакетов, исходную ветку или release tag по факту одного docs-only изменения. Версию и номер коммита/сборки указывать раздельно.

## 5. Архитектура, модель и сохранность данных

- Текущая база: **C++20, JUCE 9.0.2, CMake, Windows Desktop**, версионированный локальный JSON. Разделение: `WorkspaceModel/Store`, `Commands/Queries/Controller`, `WorkspaceShell`, `BlockEditor/Session`. UI изменяет состояние **через доменные команды**, а не прямой записью JSON.
- Одна каноническая задача и один владелец. Сегодня, страницы, календарь, Timeline, GPT и внешние источники показывают ту же запись или **ссылку**, но не создают редактируемые копии. Устойчивый ID не заменяется именем, позицией или путём файла.
- Сохранять task/checkpoint/page/block IDs, Notes keys, свойства, P1–P4, статусы, порядок, архивы, историю и backups. Отсутствующий музыкальный файл не является основанием для удаления локальных задач.
- Любая миграция схемы — отдельный подтверждённый срез: совместимость, точный backup, атомарное/проверенное сохранение, recovery, повторный запуск и защита от повреждённой/новой схемы. Отказ записи или конфликт **не должен терять черновик**. Архив/восстановление не меняют IDs.
- Не считать ручной статус равным progress и не менять его автоматически. Старый Manager DONE/count и MR Live recursive progress имеют разную семантику — контракт определять явно, не переносить формулу молча.

## 6. MR UDS и поведение интерфейса

- Канонический дизайн и SVG — в **MR-Studio `assets/ui/mr-uds/`**. Для Manager использовать закреплённую ревизию Manager Kit, manifest/catalog/tokens, указанные в MR-ECOSYSTEM и #47; прежде чем создавать иконку, проверять существующие. Не поддерживать второй независимо редактируемый SVG kit.
- Графитовый компактный Manager-профиль, тонкие контуры, 4px ритм и динамические подписи/состояния. `reference SVG` содержит демонстрационные значения — не вставлять их как пользовательские данные; ресурсы встраивать/пакетировать **офлайн**, без загрузки из GitHub во время работы приложения. Не запускать генератор kit без проверки перезаписываемых файлов.
- Для страниц/задач ориентир **Notion-like UX**, зафиксированный в #47 и `docs/NOTION-STYLE-EDITOR.md` в ветке UI: прямой ввод в документе, компактная таблица, двойной клик по Notes/названию, раскрытие задач и checkpoint, создание подзадачи на месте, ПКМ для действий, корректные Enter/Esc/blur/Undo/autosave.
- Сохранять доступность, реальную область попадания мыши, клавиатурный фокус, выделение, контраст и обратимость редактирования. Не выдавать одноуровневые checkpoint records за поддержку произвольного дерева подзадач. Не копировать DAW transport, M/S/R или метры в Manager как декоративную функциональность.
- Косметика, изменение геометрии и изменение **поведения** — разные уровни риска и проверки. Не перекрашивать MR Studio/Live глобально в рамках задачи Manager.

## 7. MR Live → Manager → MR Studio

- Первый источник — **самостоятельный MR Live** с native `.mrlive`; сначала #48 (контракт и адаптер), затем #49 (MR Studio). Browser layout, demo show и native show имеют **разные схемы**, не считать опубликованный макет готовым API.
- До интеграции подтвердить **постоянные source/document/item/task/checkpoint IDs**, владельцев полей, версии/ревизии, Browser saved vs working item, повторы item в setlist, статусы, приоритеты и progress. Повторные вхождения одного item не создают новые задачи.
- Первый snapshot/metadata export, если нет подтверждённого command bridge, явно **read-only** со временем, revision и состоянием stale/missing. Не называть его двусторонней синхронизацией.
- Write-back принимать **отдельно**, только через команды владельца с revision guard, Undo, save и recovery. Не переписывать открытый `.mrlive` или `.mrsproject` целиком со стороны Manager; предусмотреть offline/relink/конфликты/повторы.
- Manager не создаёт и не модифицирует аудиодвижок, DSP, транспорт и plugin host. Никакой файловой/сетевой сериализации в audio callback Live; отказ Manager не должен блокировать выступление.
- Будущие соцсети/GPT: доступ и API подтверждать перед реализацией; токены и секреты не коммитить, не экспортировать и не отправлять в логи; GPT предлагает проверяемые команды, а не напрямую изменяет исходные файлы.

## 8. Проверки и экономия CI

Выбирать **минимально достаточные проверки по фактическому изменению**, не одинаковый полный цикл на любой коммит.

| Изменение | Минимальные проверки |
| --- | --- |
| Только `.md`/документация | Diff, логика, ссылки/пути. **Сборка и CTest не нужны.** |
| Только цвет/иконка/толщина контура без изменения геометрии/поведения | Diff и корректность ресурса; адресная сборка Desktop, только если нужно получить обновлённый EXE. Без автоматических массовых GUI/DPI/CTest проверок. |
| Геометрия или поведение GUI | Затронутые UI/unit-тесты, сохранение фокуса/ввода/черновика и профильные native snapshots; Windows-кандидат по согласованной проверке. |
| Модель/команды/JSON-миграция | Тесты владельца/ID, архивов/backup, конфликтов, recovery, неизвестной схемы, restart. |
| Adapter/source contract | Fixtures, revision/stale/missing, повторное связывание, защита от дублей, статусы/progress и границы read-only/write-back. |

- Для текущей кодовой базы релевантны `WorkspaceTests`, `WorkspaceNavigationTests`, `BlockEditorTests`, `SongCatalogTests` и добавляемые в тематических ветках `GeneralTaskTests`/`TaskTreeUiTests`. Названия и доступность проверять по **рабочей ветке**, не считать отсутствующие в main наборы уже существующими.
- Полный Windows workflow/CTest — для согласованного интеграционного/релизного кандидата или обоснованного риска, а не ради docs-only и мелкой косметики. **Не запускать вручную** новую тяжёлую сборку без просьбы пользователя; учитывать, что PR может автоматически запустить уже настроенный GitHub Actions.
- Отличать **PASS / FAIL / NOT TESTED**. Успешный Windows CI не заменяет пользовательскую проверку EXE, физического DPI и поведения. Не утверждать, что ASIO, Live или сторонние файлы испытаны, если их не проверяли.
- Не удалять и не перезаписывать реальные пользовательские проекты при тестировании; использовать отдельные fixtures.

## 9. Отчёт и передача следующему чату

- В конце работы: **Issue/PR/branch/commit**, что изменено, какие тесты реально прошли, что не проверено, где артефакт, что требуется от пользователя. Нет приёмки — явно писать «ожидает приёмки», без merge.
- Обновлять тематическую документацию, когда меняется **контракт или решение**, а не вести в ней дублирующую хронику каждой сборки. При необходимости обновить HANDOFF/ROADMAP и конкретный Issue.
- Следующему чату достаточно этого файла, назначенного Issue и профильных документов; **сначала проверить GitHub**, не полагаться только на пересказ старого разговора.
